# Feature Specification: Multi-agent UI Testing Loop

**Feature Branch**: `002-multi-agent-ui-loop`  
**Created**: 2025-12-10  
**Status**: Draft  
**Input**: User description: "$ARGUMENTS"

本特性旨在基于用户自然语言需求，构建一个由多个智能体协作完成的 UI 生成与测试闭环：从 UI 初次生成，到测试用例设计、UI 自动化测试、问题分析与反馈，再到 UI 迭代优化与回归验证，形成 Evaluator-Optimizer 模式下的自反馈闭环。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一键从需求到可用 UI 闭环 (Priority: P1)

作为一名产品或设计同学，我希望只用自然语言描述某个页面/功能的需求，系统就能自动完成 UI 初次生成、关键用户路径的测试用例设计、串行执行 UI 测试，并在所有关键用例通过后生成一份简明的测试报告，这样我可以在不懂测试脚本或自动化框架的前提下，快速拿到一个“可用且已基本验证”的 UI 初版。

**Why this priority**: 这是整个多智能体系统的核心价值闭环（从需求到可用 UI），能够在没有工程背景的情况下大幅降低 UI 验证门槛，因此作为 P1 优先实现。

**Independent Test**: 仅实现“从需求到单次完整闭环（首次 UI 生成 + 一轮测试 + 报告）”也可以对外展示：给定一段自然语言需求，用户点击开始后，系统最终产出一套 UI 及对应测试通过的报告，全程无需用户干预即可作为 MVP 价值验证。

**Acceptance Scenarios**:

1. **Given** 用户输入一段清晰的自然语言 UI 需求，**When** 用户触发“生成并测试”操作，**Then** 系统依次完成 UI 生成、测试用例设计、按用例串行执行 UI 测试并在所有用例通过后生成测试报告，最终用户能看到 UI 预览和测试结果概览。
2. **Given** 用户输入的需求存在一定模糊但仍可被理解，**When** 系统运行完整闭环流程，**Then** UI 生成和测试执行仍能顺利完成，报告中会明确标注哪些行为是基于系统假设完成的，并提示可能需要用户后续细化需求。

---

### User Story 2 - 单个失败用例驱动 UI 迭代 (Priority: P1)

作为一名关注交互质量的用户，我希望当某个测试用例在 UI 测试阶段失败时，系统可以自动把失败原因和上下文反馈给 UI 修改智能体，对 UI 进行有针对性的调整，再在必要的范围内重新运行相关用例，直到通过或达到设定的迭代上限，这样我可以得到经过数轮优化的 UI，而不需要自己逐一阅读日志和手动改 UI。

**Why this priority**: Evaluator-Optimizer 自反馈闭环是本特性的核心创新点。没有这部分，系统只是一轮性的“生成 + 测试”工具，而非能够自我迭代的多智能体系统，因此与 User Story 1 同为 P1。

**Independent Test**: 即便只支持“对单个失败用例进行一轮自动修复和重测”，也能作为独立价值点：给定一套已有 UI 和一个失败用例，系统自动提出并应用 UI 修改，再重新执行该用例并反馈结果。

**Acceptance Scenarios**:

1. **Given** 某条测试用例在执行中失败（例如按钮不可点击或期望文案缺失），**When** 失败信息被发送给 UI 修改智能体，**Then** 系统会基于失败上下文生成明确的修改意图，对 UI 进行修改并重新执行该失败用例，若通过则在测试结果中记录“由失败驱动的一次成功修复”。
2. **Given** 某条测试用例多次修复尝试后仍失败，**When** 迭代次数达到预设上限，**Then** 系统会停止进一步自动修改，明确在结果中标注“需要人工介入”的原因说明和最后一次失败的详细信息。

---

### User Story 3 - 分阶段可视化查看各 Agent 贡献 (Priority: P2)

作为一名希望理解多智能体协作过程的高级用户或研发同学，我希望可以在 UI 上看到“需求理解 → UI 生成 → 测试用例设计 → 测试执行 → 结果分析 → UI 迭代”的阶段视图，以及每个阶段由哪个 Agent 负责、做了什么决策和输出了什么结果，这样我可以理解整个闭环的工作方式，并在必要时对某个阶段的行为进行复盘和调整。

**Why this priority**: 阶段可视化并非最小可用闭环所必需，但对于调试、迭代和用户信任度非常关键，有助于后续优化 Agent 角色划分，因此设为 P2。

**Independent Test**: 即使仅提供“静态阶段时间线 + 每个阶段的高层结果摘要”，也可以独立测试：用户发起一次闭环运行后，可以回看整个过程中的阶段顺序、Agent 角色和关键输出。

**Acceptance Scenarios**:

1. **Given** 用户发起了一次从需求到 UI 的完整闭环，**When** 闭环完成后用户打开“过程视图”，**Then** 用户可以按时间顺序看到各阶段（需求理解、UI 生成、测试设计、测试执行、结果分析、UI 迭代）以及每个阶段对应的高层文本摘要或关键指标。
2. **Given** 在某些用例执行失败并触发了 UI 迭代，**When** 用户查看过程视图，**Then** 可以清晰区分“原始 UI”与“若干次迭代后的 UI”，并看到每次迭代是由哪条失败用例触发的。

---

### User Story 4 - 针对已有 UI 进行回归与扩展测试 (Priority: P3)

作为一名已有 UI 项目的维护者，我希望在不重新从零生成 UI 的情况下，把现有 UI 和一段新的业务变更说明交给系统，让其在此基础上自动生成补充性的测试用例，并通过多智能体协作完成测试与必要的 UI 迭代，这样可以将系统用于“已有项目的回归与增强测试”，而不仅仅是全新 UI 生成场景。

**Why this priority**: 这是扩展场景，可以显著提升系统在真实项目中的适用范围，但不影响首版闭环在新建 UI 场景下的可用性，因此设为 P3。

**Independent Test**: 提供一个已有 UI 的入口（例如上传或选择已有组件），再输入一段变更说明，验证系统是否能够在不破坏原有核心结构的前提下，设计并执行补充测试，并在失败时触发局部 UI 调整。

**Acceptance Scenarios**:

1. **Given** 用户选择了一个已有 UI 并输入一段新增需求说明，**When** 系统基于当前 UI 和新增需求生成测试用例并执行，**Then** 测试结果可以区分“原有用例”与“新增用例”的执行情况。
2. **Given** 新增用例中出现失败，**When** 系统触发 UI 迭代，**Then** 修改范围会尽量局限在与新增需求相关的部分，并在结果中提示“本次迭代基于已有 UI 场景进行局部调整”。

---

### Edge Cases

- 当用户需求极度模糊或互相矛盾时，系统应能够检测到无法构建合理的测试用例集合，并在开始执行前向用户反馈“需求不充分/自相矛盾”，而不是盲目生成不可测试的 UI。
- 当某个测试用例在执行时遇到无法稳定复现的行为（例如偶发性加载问题），系统应避免无限重试，限制重试次数，并在报告中标记为“结果不确定”的边界情况。
- 当多条测试用例指向同一类 UI 问题（例如多个入口都无法完成提交动作）时，系统在触发 UI 迭代时应聚合这些信号，避免对同一问题做多次结构相似的修改尝试。
- 当用户中途取消执行或关闭页面时，系统应能在下一次恢复时提供最近一次完整或部分完成的闭环结果，并明确哪些阶段已经完成、哪些尚未开始或中断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持用户使用自然语言描述 UI 需求，并将其转化为可供后续各智能体共享理解的内部表示，用于驱动 UI 生成与测试用例设计。
- **FR-002**: 系统必须具备 UI 生成智能体，能够基于需求表示生成初始 UI，并在收到后续迭代指令时对已有 UI 进行增量修改，而不是每次从零开始重建。
- **FR-003**: 系统必须具备测试用例生成智能体，能够基于用户需求和当前 UI 状态，生成覆盖主要用户路径的多条测试用例，包括正向路径、常见异常输入以及基础可用性检查。
- **FR-004**: 系统必须具备 UI 测试执行能力，能够针对每条测试用例依次在同一 UI 上执行操作步骤，记录每一步的关键状态与预期/实际结果，并在出现错误时停止当前用例并输出原因。
- **FR-005**: 系统必须具备结果分析能力，能够判断每条测试用例的通过/失败状态，对失败原因进行归类，并根据失败类型决定是否需要触发 UI 迭代。
- **FR-006**: 系统必须具备 UI 修改智能体（优化器角色），在接收到失败用例及其上下文后，给出明确的 UI 修改方案并应用于当前 UI，再触发与该失败用例相关的回归测试。
- **FR-007**: 系统必须支持串行调度多个测试用例，避免并发修改同一 UI 状态导致的相互干扰，同时允许在逻辑上对失败用例进行优先处理（例如一旦发现关键路径失败，可提前中断后续次要用例）。
- **FR-008**: 系统必须在所有高优先级测试用例通过后生成一份测试报告，包含用例列表、执行结果统计、失败/修复历史以及最终 UI 状态的高层描述，便于用户决策是否接受当前 UI 版本。
- **FR-009**: 系统必须向用户暴露多智能体协作过程的高层状态（例如当前阶段和负责的 Agent 角色），以便用户理解系统正在做什么，而无需了解底层实现细节。
- **FR-010**: 当系统遇到无法自动修复的问题（如达到最大迭代次数、存在结构性需求冲突等）时，必须向用户提供清晰的人类可读说明，并避免继续进行无效的自动尝试。

*补充要求：*

- **FR-011**: 系统在单次闭环中最多允许 3 轮“UI 修改 + 测试”自动迭代，当达到 3 轮仍未解决相关问题时，必须停止自动尝试并在结果中明确提示需要人工介入。
- **FR-012**: 测试用例生成时必须按照如下优先级分配覆盖深度：优先覆盖“核心业务路径”，其后是“基础可用性/可访问性检查”，最后是“边缘错误场景”，并在报告中反映各类场景的覆盖情况。
- **FR-013**: 当失败用例触发 UI 迭代时，系统可以在不影响内容可读性与基本可用性的前提下，对任何 UI 元素进行自动调整（包括颜色、排版和布局等），以提高通过率，不做品牌风格层面的强约束，前提是在测试环境中使用并在结果中予以说明。

### Key Entities *(include if feature involves data)*

- **用户需求描述**：表示用户以自然语言提供的 UI 目标和业务规则的文本，以及系统从中抽取的结构化要点（如页面目标、关键操作、约束条件）。
- **UI 版本**：表示在闭环过程中某一时刻的 UI 状态，每次 UI 修改都会形成新的版本，并关联来源（初始生成或由哪次失败用例触发的迭代）。
- **测试用例**：表示一条从初始状态到期望结果的可执行步骤序列，包括前置条件、操作步骤、预期结果和优先级，用于指导 UI 测试执行。
- **测试执行结果**：表示每条测试用例的执行记录，包括时间、步骤级别状态、通过/失败标记及失败时的错误信息、截图或关键日志引用。
- **迭代会话**：表示一次从初始 UI 到若干轮修改和测试的闭环过程，包含参与的各智能体角色、阶段顺序、关键决策和最终输出（UI 版本与测试报告）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对于清晰的单页面需求描述，从用户发起到闭环完成（UI 生成 + 主要用例设计 + 测试执行 + 报告生成）的时间，在普通规模页面场景下应有 80% 以上的任务能够在 5 分钟内完成。
- **SC-002**: 在代表性需求样本上，系统自动生成的测试用例集合应能覆盖至少 80% 的核心用户路径（以专家人工标注的理想用例集合作为对比基准）。
- **SC-003**: 对于简单到中等复杂度的需求，在至少 70% 的场景中，系统应能通过 0~2 轮自动 UI 迭代解决由自身发现的可用性或流程性问题，而无需人工介入。
- **SC-004**: 在试点用户中，至少 80% 的用户认为“相比手动生成 UI + 手动写测试用例 + 手动执行测试”，本系统在整体效率上有明显提升（例如通过问卷调查或任务完成时间对比评估）。
- **SC-005**: 在测试运行中，对于可稳定复现的 UI 问题，系统应能在 95% 以上的场景中给出明确的错误定位（例如指出具体元素或交互步骤），而不是仅返回“用例失败”的笼统结论。
